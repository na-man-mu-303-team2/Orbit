# 김동현(kdh949)의 ORBIT 기여

ORBIT는 AI 발표자료 생성, Canvas 편집, 리허설 코칭과 실전 발표·청중 참여를 하나의 제품으로 연결한 팀 프로젝트입니다. 이 문서는 팀 전체 결과와 개인 담당 범위를 구분하고, 공개 저장소에서 확인할 수 있는 대표 구현 두 가지를 정리합니다.

## 담당 범위

- 발표 메모와 리허설·발표 경험
- 실시간 청중 참여용 Activity Slides
- 대용량 PPTX OOXML generation·sync 처리
- Worker 실패 상태와 운영 검증

대표 사례는 다음 두 가지입니다.

1. **Activity Slides 통합** — 편집기, 발표자, 청중 응답, 결과 보관·내보내기를 하나의 제품 흐름으로 연결
2. **PPTX Worker OOM 개선** — Node Worker가 대용량 Base64 JSON을 중계하던 경로를 Object Storage 직접 업로드와 Manifest 계약으로 변경

## 1. Activity Slides를 편집부터 발표·보관까지 연결

관련 PR: [#436 참여 장표(Activity Slides) MVP 통합](https://github.com/na-man-mu-303-team2/Orbit/pull/436)

### 문제

실시간 투표·평점·자유 응답 기능은 청중이 답하는 화면만으로 끝나지 않습니다. 편집기에서 질문을 만들고, 발표 중 응답을 받고, 발표자만 볼 수 있는 결과를 갱신하고, 세션이 끝난 뒤 결과를 보관·내보내는 과정이 하나의 계약으로 이어져야 했습니다.

또한 첫 응답 이후 질문 정의가 바뀌면 같은 실행 안에서 서로 다른 질문에 대한 응답이 섞일 수 있고, 공개 DTO나 내보내기 결과에 표시 이름·미검토 원문·발표자 전용 정보가 포함될 위험이 있었습니다.

### 판단

Activity를 단일 화면 기능이 아니라 다음 경계를 가진 제품 흐름으로 설계했습니다.

- 첫 응답 이후 질문의 의미가 바뀌는 필드는 잠그고, 변경이 필요하면 새 run version 생성
- 청중 입장 성공 인원을 기준으로 응답률 계산
- 응답 원문과 표시 이름은 발표자·moderation 범위에서만 사용
- 보관 기간이 지난 식별 행은 제거하되 익명 count·rate snapshot은 유지
- PPTX·PNG ZIP 내보내기에는 live QR, 미검토 주관식 원문과 발표자 전용 정보를 포함하지 않음

### 구현 범위

통합 PR에서 다음 child PR stack을 하나의 release gate로 묶었습니다.

- 공통 Activity 계약과 편집기 기반
- PresentationSession과 Activity runtime
- 청중 참여·응답 API와 실시간 갱신
- 발표자 결과·moderation
- 결과 장표와 session archive
- retention, export, 성능·보안 검증과 E2E
- 편집기 실행 잠금, 응답률과 익명 보존

### 검증 결과

PR #436의 기준 환경에서 다음을 확인했습니다.

- workspace build, lint, test, typecheck 통과
- Playwright 전체 흐름 1개 통과
- 200명 동시 응답: **200/200 응답**
- HTTP 응답 지연: **p50 203ms, p95 325ms**
- 첫 응답 이후 definition 불변성과 새 run version 경계
- 표시 이름·미검토 주관식 원문·발표자 script의 청중 비노출
- 익명 snapshot을 남긴 뒤 식별 행을 제거하는 retention과 재실행 안전성

위 수치는 PR #436에 기록된 해당 부하 테스트 환경의 결과입니다.

## 2. Base64 중계를 제거해 PPTX Worker OOM 경로 개선

관련 PR: [#619 PPTX OOXML Worker OOM 개선](https://github.com/na-man-mu-303-team2/Orbit/pull/619)

### 관찰한 장애

사용자 화면에는 `PPTX OOXML generation job timed out`이 보였지만, 실제 흐름은 다음과 같았습니다.

1. `pptx-ooxml-generation` Job 시작
2. Python Worker가 처리를 마치고 `200 OK` 반환
3. Node Worker가 대형 Base64 asset JSON을 수신·파싱·decode하는 구간에서 메모리 한도 초과
4. Node 프로세스가 `SIGKILL`로 종료되고 Docker에 `OOMKilled=true` 기록
5. BullMQ 처리와 DB Job terminal 상태 갱신이 끝나지 않음
6. Web이 `queued`·`running`을 polling하다 120초 뒤 timeout 표시

따라서 Web timeout은 원인이 아니라, Worker가 종료된 뒤 Job 상태가 닫히지 않아 나타난 결과로 판단했습니다.

### 근본 원인

기존 generation 응답은 이미지와 PPTX package를 `contentBase64`가 들어 있는 JSON으로 Node Worker에 한 번에 반환했습니다. Node에는 HTTP body, JSON 문자열, 파싱 결과, decoded Buffer, storage 업로드 body와 해시 처리 중 임시 참조가 동시에 존재할 수 있었습니다.

sync 입력에서도 Node가 Storage object를 내려받아 `arrayBuffer` 또는 Base64로 만든 뒤 Python Worker에 전달해 같은 종류의 메모리 증폭이 발생할 수 있었습니다.

### 변경 전후

```text
변경 전
Python Worker
  → 대형 Base64 JSON
  → Node JSON parse·Base64 decode
  → Node가 Object Storage에 업로드
  → DB asset 등록

변경 후
Python Worker
  → asset별 S3·MinIO 직접 업로드
  → storage-manifest-v1 반환
  → Node가 HEAD metadata 검증
  → DB asset 등록
```

sync 입력은 다음과 같이 바꿨습니다.

```text
변경 전
Storage → Node download·Buffer·Base64 → Python Worker

변경 후
Node → signed read locator → Python Worker가 허용된 Storage origin에서 직접 fetch
```

### 핵심 구현

#### `storage-manifest-v1` 공통 계약

Manifest에는 `assetId`, `fileName`, `mimeType`, `storageKey`, `size`, `sha256`만 포함합니다. 공통 Zod schema에서 경로 형식, 개수·크기 상한, digest 형식과 선언되지 않은 필드를 검사합니다.

#### Python Worker 직접 업로드

- asset을 Job 전용 prefix 아래 S3·MinIO에 순차 업로드
- SHA-256을 계산해 object metadata에 기록
- 성공 응답에는 binary·Base64 대신 Manifest만 포함
- 중간 실패 시 이미 올라간 partial object를 best-effort cleanup

#### Node Worker의 body-free 등록

Node는 binary body를 보유하지 않고 다음을 검증합니다.

- 예상 Job prefix와 storage key
- asset ID·storage key 중복
- object 존재 여부
- content length·MIME·SHA-256 일치

검증된 asset은 결정적 file ID로 등록하고, asset·Deck·TemplateBlueprint와 프로젝트 상태 변경을 같은 DB transaction 안에서 처리합니다.

#### 실패 상태 수렴과 관찰성

- BullMQ 최종 실패·stalled 상태와 DB Job의 `failed` 상태를 맞춤
- Worker를 watch/compiler가 없는 compiled production 실행으로 변경
- Worker·Python Worker memory limit과 restart policy 추가
- Job 로그에 RSS, heap, external, array buffer와 max RSS 기록
- Base64, 발표자 script와 raw audio 같은 대용량·민감 payload는 로그에서 제외
- 장애 판별, rollout·rollback과 상태 확인 순서를 runbook에 정리

### 검증 범위

PR #619의 clean worktree에서 기록된 검증 결과입니다.

| 영역 | 결과 |
| --- | --- |
| OOXML Worker 관련 테스트 | 71 passed |
| Job Queue 테스트 | 29 passed |
| Shared package 전체 테스트 | 588 passed |
| Storage package 테스트 | 4 passed |
| Python Worker 전체 회귀 테스트 | 835 passed |
| Python 정적 검사 | `ruff check .`, `mypy app` 통과 |
| Web·Worker build | 통과 |
| 환경·Container 계약 | env check와 Compose config 통과 |

테스트 수는 각 저장소 범위에서 통과한 개수이며, 개인이 새로 작성한 테스트 수를 의미하지 않습니다. 이 변경에는 동일 파일을 사용한 전후 peak RSS 비교 수치가 없으므로 처리량 배수나 메모리 절감률을 성과로 사용하지 않습니다.

## 두 사례에서 공통으로 적용한 기준

- 화면에 보이는 오류보다 Job, 프로세스, DB와 Storage의 실제 상태를 먼저 확인했습니다.
- 데이터의 기준 원천과 변경 책임을 공통 계약으로 명시했습니다.
- 정상 처리뿐 아니라 중복 실행, 부분 실패, 재시도와 보관 기간 이후 상태를 함께 정의했습니다.
- 팀 전체 결과와 개인 담당 범위, 작성한 테스트와 전체 회귀 테스트를 구분했습니다.
- AI 코딩 도구는 코드 탐색과 구현 초안에 사용하되 문제 정의, 경계 선택, 적용 범위와 최종 검증은 직접 판단했습니다.
