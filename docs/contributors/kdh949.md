## 1. 대용량 PPTX 처리 중 Node Worker OOM

### 관찰한 현상

사용자 화면에는 `PPTX OOXML generation job timed out`이 표시됐지만, 로그와 컨테이너 상태를 따라가면 실제 장애 순서는 달랐습니다.

1. `pptx-ooxml-generation` Job 시작
2. Python Worker가 PPTX 처리를 마치고 `200 OK` 반환
3. Node Worker가 대형 Base64 JSON을 수신·파싱·디코딩하는 과정에서 메모리 한도 초과
4. Node 프로세스가 `SIGKILL`되고 Docker에 `OOMKilled=true` 기록
5. BullMQ와 DB Job 상태가 종료되지 않은 채 남음
6. Web이 120초 뒤 Timeout을 표시

따라서 Timeout은 직접 원인이 아니라 Worker 종료 뒤 Job 상태가 닫히지 않아 나타난 결과로 판단했습니다.

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| Worker 메모리 증설 | 장애 시점을 늦출 뿐 Base64 복사 경로를 유지함 |
| Web Timeout 연장 | 정상 대형 파일의 여유는 늘지만 Worker OOM을 해결하지 못함 |
| Node streaming | 메모리 사용을 줄일 수 있으나 Python→Node→Storage 중계와 계약 복잡도가 남음 |
| 공유 볼륨 | 로컬에서는 단순하지만 배포 환경과 결합도가 커짐 |
| Python 직접 업로드 | Node를 대형 바이너리 데이터 경로에서 제외하고 작은 계약만 전달할 수 있음 |

### 변경한 구조

```text
변경 전
Python Worker
  → 대형 Base64 JSON
  → Node JSON parse
  → Base64 decode Buffer
  → Node가 Object Storage에 업로드
  → DB 등록

변경 후
Python Worker
  → Object Storage에 asset별 순차 업로드
  → storage-manifest-v1 반환
  → Node가 위치·크기·MIME·SHA-256 Metadata 확인
  → DB transaction으로 asset과 Deck 참조 등록
```

Generation 출력뿐 아니라 Sync 입력·출력에서도 Node가 대형 파일을 내려받아 Buffer와 Base64로 다시 만드는 경로를 제거했습니다. Python Worker에는 허용된 Storage origin의 signed read locator만 전달하고, Node는 바이너리 대신 bounded metadata를 다룹니다.

### 실패 처리와 검증

- Job 전용 Storage prefix와 경로 형식 확인
- asset ID·Storage key 중복, 개수와 총량 상한 확인
- Object `HEAD`의 크기·MIME·SHA-256과 Manifest 일치 여부 확인
- 중간 실패 시 부분 업로드 정리
- BullMQ retry·stalled 상태와 DB Job의 `failed` 상태 수렴
- Worker 메모리 지표와 운영 Runbook 추가

PR 검증 기록은 다음 범위를 포함합니다.

- OOXML Worker 관련 테스트 71개 통과
- Job Queue 테스트 29개 통과
- Python Worker 전체 회귀 테스트 835개 통과
- Python `ruff`, `mypy`와 Web·Worker build 통과

## 2. Activity Slides 통합

실시간 투표·질문·만족도 조사 같은 참여 장표를 편집기에서 만들고, 발표 중 청중이 응답하며, 결과를 보관·내보내는 전체 흐름의 통합 PR을 맡았습니다.

### 주요 경계

- 첫 응답 이후 질문과 선택지의 의미가 바뀌지 않도록 Definition fingerprint와 실행 버전을 분리
- 발표자에게만 필요한 응답률·원문·moderation 상태와 청중 공개 결과를 별도 projection으로 구성
- 90일 뒤 식별 가능한 응답 행을 삭제하고 익명 집계 snapshot만 보존
- PPTX·PNG ZIP 내보내기에서 QR, 표시 이름, 대기 중 원문과 발표자 전용 정보를 제외
- Redis rate limit, Origin·Content-Type 검증과 plain-text 렌더링 적용

### 검증 기록

- 편집기 → 발표 세션 → 청중 응답 → moderation → 결과 공개 → archive → export → retention Playwright 흐름 통과
- 실제 PostgreSQL·Redis·Socket.IO 환경에서 200명 동시 응답 200/200
- 측정 기록: HTTP p50 203ms, p95 325ms, event→snapshot 8ms
- API, Shared, Python Worker, migration `run → revert → run`과 환경 계약 검증 통과

이 수치는 PR의 로컬·검증 환경에서 측정한 결과이며 운영 서비스 SLO를 의미하지 않습니다.

## 3. iPad 발표자 Companion

발표자가 iPad로 현재 슬라이드를 확인하고, 페이지 이동·필기·레이저·화면 공유를 제어하도록 페어링부터 재연결까지의 수직 기능을 구현했습니다.

### 주요 설계 판단

- Pairing code를 원문 Redis key나 로그에 남기지 않고 HMAC key로 한 번만 사용
- 한 세션의 제어권은 10초 Authority lease와 3초 heartbeat로 관리
- Authority epoch으로 이전 발표자 창의 명령을, companion generation으로 이전 iPad 연결을 차단
- 검은 화면에서는 복귀 위치만 유지하고 필기 surface·laser·snapshot을 발행하지 않음
- Screen share는 video track만 전달하고 `shareEpochId`, `signalId`, authority와 generation을 함께 확인
- Speaker notes, 전체 script, raw transcript·audio와 SDP·ICE를 청중 API·DOM·로그에 노출하지 않음
- iPad 연결 실패가 기존 발표·리허설 시작을 막지 않도록 기능 flag와 우회 경로 유지

### 검증 기록

- Pairing, authority, reconnect, black output, WebRTC와 asset 경계 회귀 테스트
- 실제 Socket.IO integration과 migration `run → revert → run`
- 10분 synthetic 60Hz annotation soak
- Chromium companion smoke 5개 통과
- PC와 iPad landscape·portrait Product Design QA 수행

초기 통합 뒤에도 실제 화면 전환에서 발견된 authority 상태 문제를 [PR #663](https://github.com/na-man-mu-303-team2/Orbit/pull/663)에서 원인 분석하고 자동 재접속과 안전한 slide fallback을 보강했습니다.

관련 문서: [iPad Presenter Companion QA](../qa/ipad-presenter-companion.md)

## 개인 기여를 설명하는 기준

- 팀 제품 전체 기능을 개인 성과로 묶지 않고, 직접 작성·통합한 PR과 판단 범위를 구분합니다.
- 테스트 개수는 직접 작성한 수가 아니라 해당 PR 검증에서 통과한 전체 또는 관련 스위트의 범위로 표시합니다.
- OOM 개선은 Node의 대용량 바이너리 중계 경로를 제거한 구조 변경으로 설명하며, 기록하지 않은 전후 Peak RSS나 처리량 개선 수치는 사용하지 않습니다.
